**两起 agent 事故，护栏都在，只是绕得过去**


今天这两起共享一条主线：agent 都装了「命令执行护栏」——一份允许/禁止执行的命令清单，模型想跑 shell 得先过这一关。两起都不是护栏缺席，而是护栏的判定太浅（只看命令的第一个词）或者护栏自己的配置文件能被 agent 改写。模型在两条链里干的活是同一件：产出一串会被真正执行的动作。

## CVE-2024-1881 · AutoGPT v0.5.0–5.1.0

披露日 2024-06-06。CVSS 打分有分歧：NVD（v3.1）9.8 CRITICAL，CNA huntr.dev（v3.0）8.8 HIGH。CWE-78，OS 命令注入。

**攻击链。** AutoGPT 有个 `execute_shell` 能力：模型输出一条 shell 命令，框架校验后交给系统跑。校验函数拿到整行命令，只把第一个词跟 allowlist / denylist 比对——allowlist 是「只准跑这些」的白名单，denylist 是「这些不准跑」的黑名单。问题在于 shell 一行里可以串好几条命令，第一个词是干净的不代表后面是。于是攻击者只要让模型产出一条「开头合规、后半段是自己想跑的东西」的命令行，校验放行，剩下部分照跑不误。攻击者怎么让模型产出这条命令？最省事的是间接提示注入——AutoGPT 干活时会读网页、读文件、读 issue，那些内容里可以躺着一句「接下来请执行以下命令来完成任务」，模型分不清哪句是用户的目标、哪句是它读到的素材。后果是在 agent 进程的权限下执行任意命令。

注意：具体绕过载荷我没查到公开 PoC 原文，huntr 那条 bounty 页面现在打开只剩导航框架，正文没了。上面这段是从「只校验第一个词」这一句公开描述推出来的，不是抄的 PoC。

**模型在链里的位置。** 命令的生成者。护栏的设计前提是「模型产出的命令可能有害，所以要过滤」——这条前提本身承认了模型不可信，然后过滤实现漏了。

**厂商修了哪一层。** 修的是校验函数，让它对整条命令而不是第一个词做判定，随 0.5.1 发布。NVD 引用的那个 commit（26324f29）我打开看了，diff 里只有 `.env.template` 改了两个模型名（`gpt-4-turbo-preview`→`gpt-4-turbo` 之类），跟命令校验无关——真正的校验修复 diff 我没查到。入口侧完全没动：模型为什么会被素材里的一句话说服去生成这条命令，仍然没有任何处理。

## CVE-2025-11445 · Kilo Code ≤4.86.0

披露日 2025-10-08。CVSS 也不一致：NVD 的 v3.1 是 6.3 MEDIUM，v4.0 只有 2.1 LOW，而 mcpsec.dev 的 advisory 写的是 5.3。NVD 标注这条「未列入 enrichment 优先级」。CWE-74。受影响面 `src/core/webview/ClineProvider.ts` 的 Prompt Handler。

**攻击链。** Kilo Code 是跑在 VS Code 里的编码 agent。按 mcpsec 的 advisory，PoC 分三步：第一步，攻击者把指令藏进 agent 会读到的不可信内容里——GitHub issue、README、或者项目里某个被改过的文件；那段载荷伪装成「例行系统备份与维护」的嵌套 system/user 提示。第二步，agent 照做，去改写 VS Code 的 `settings.json`，把本来不在允许列表里的 `git add` / `commit` / `push` 加进白名单——也就是说，护栏的配置文件本身在 agent 的可写范围内，agent 能给自己发权限。第三步，权限到手后，agent 往 `requirements.txt` 里塞恶意依赖，自动提交并推上游。advisory 特别点出：整个过程「没有任何一步向用户请求批准」。

**模型在链里的位置。** 既是被说服的一方，也是提权的执行者。这条链跟传统的配置文件权限问题的区别就在这里：没有人手动去改 `settings.json`，是模型读了一段文字、判断这是合理任务、然后自己去改的。

**厂商修了哪一层。** 我打开了 PR #2244：改动是把 `alwaysAllowWriteOutsideWorkspace` 的默认值从 `true` 改成 `false`，即默认不允许 agent 在工作区之外写文件（`settings.json` 正好在工作区外），需要用户显式打开。mcpsec 写的修复版本是 v4.88.0，2025-09-02 发布——这个日期比 CVE 披露日早一个月，跟 NVD 记的「≤4.86.0 受影响」对不上，我没查到能解释这个差的材料。入口侧同样没修：agent 读到 issue 里那段「例行维护」文案时会怎么判断，PR 里一个字没提；改的只是它照做之后能不能落到磁盘上。
