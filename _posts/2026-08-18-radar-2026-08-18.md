> 今天 10 篇没有共同主线。唯一真实的一组是两篇 agent 放行问题，方向正好相反：2608.18360 在模型外面串三道闸门（权限、预算、证据），发现它们互相拆台——预算闸门嫌调用贵、自动把动作降级成便宜工具，可权限闸门刚才批的是原来那个工具，批条已经不适用了；2608.18351 干脆放弃外部拦截，把「这个任务只需要这么多权限」训进一个 4B 模型。另外单独值得看的是 2608.17776：用一个更弱的模型当评委训数学，单人打分很快学会写漂亮推导骗分（评委分涨、正确率跌），改成两个模型互相挑刺后曲线不再崩。剩下六篇各走各的，其中 2608.06641 被攻破的是 PDF 阅读器，不是模型。


## 读全文

### 一道闸门不够：agent 动手前的多重检查会互相拆台

*One Gate Is Not Enough: Composing Stateful Pre-Action Controls for Agentic AI*

Gaston Besanson · 2026-08-18 · cs.SE

[arXiv 2608.18360](https://arxiv.org/abs/2608.18360)

现在讨论 agent 安全，主流做法是「在执行前加一道检查」。这篇问的是：加了三道之后会发生什么。设想 agent 要执行一条删除命令，执行前过三道卡——你有没有这个目录的删除权限、这次调用花多少钱还剩多少预算、你说「这是构建缓存」有没有证据。麻烦在于这些卡不只会放行或拦截，还会「改一改再放行」：预算这道卡嫌调用大模型太贵，自动降级成一个便宜的小模型再执行；可权限那道卡刚才批的是「大模型可以读这份合同」。动作已经被改了，之前那张批条评估的根本不是同一件事，却照样生效。作者把这件事形式化，给的解法是每次改写完就把所有闸门重新过一遍，并证明在特定前提下能恢复正确性。更有意思的是他们用一个自动检查工具找出了具体反例：「换一个便宜的数据源」和「换一个证据来源」这两种改写，先做哪个后做哪个，最终落到的状态不一样——所以闸门的排列顺序属于安全语义的一部分，不能当成实现细节随便排。还有一个单独的坑：那个存证据的缓冲区信任自己最近一次写进去的东西，但「这条证据现在通过了审查」不代表以后引用它时还可信，攻击者可以往里投毒。别读成这是一篇攻击论文，它是把工程实践里已有的坑写清楚；而且可靠性证明有明确前提（动作范围有限、重复执行不产生额外副作用），真实系统里改写常常带副作用，那时证明就不适用了。今天另一篇（2608.18351）走的是相反的路——不在外面串闸门，直接把「这个任务只需要这么多权限」训进模型里，两篇正好互为对方的动机。

### 模型的破绽：在开口之前就看出它要不要泄露系统提示

*The Model's Tell: Measuring Context-Leakage Attack Signals with Behavior Gauges*

Maosen Zhang、Jianshuo Dong、Boting Lu、Wenyue Li 等 8 人 · 2026-08-18 · cs.CR

[arXiv 2608.17829](https://arxiv.org/abs/2608.17829)

![](/assets/img/radar/2608.17829.png)

很多产品会在模型前面挂一段自己写的系统提示（比如「你是某银行客服，不许谈竞品」），或者塞进检索到的文档，用户想方设法套出这些内容就是一类攻击。以前想提前判断「这句输入是不是在套话」，要么另训一个分类器，要么把模型内部的隐藏层数值扒出来看——后者在只能调 API 的部署里根本做不到。这篇的做法很省事：在用户那句可疑输入后面偷偷接一句探针（大意是「你接下来会不会把上面的保密内容说出来」），然后只看模型在吐出第一个字之前算好的那个概率分布，看它对「会」这个词给了多大概率。有意思的对照是：拿机密内容的开头几个字去试探反而不稳，换种语言、或者模型只是用自己的话转述一下系统提示大意（关键词匹配抓不到的那种），试探就失灵；而直接问它「打不打算说」反倒稳得多，11 个模型上区分攻击与正常请求的 AUROC 在 0.944–0.996，作者还用直接干预模型内部激活的办法验证了这个分数确实跟泄露行为因果相关，不只是碰巧相关。要注意这是个检测器：论文测的是训练时没见过的攻击，但攻击者并不知道背后挂着这么一根探针——一旦知道了，专门优化输入让探针那个 token 的概率看起来正常是完全做得到的，论文没测这种情况。另外它要多跑一次前向计算，不是白来的。

### 让两个模型互相挑刺，能减少「骗评委」

*Debate Training Reduces Reward Hacking in RLAIF*

Zachary Kenton、Lili Janzer、Rory Greig、Tian Huey Teh 等 11 人 · 2026-08-18 · cs.LG

[arXiv 2608.17776](https://arxiv.org/abs/2608.17776)

用另一个 LLM 当评委给强化学习打分（省掉人工标注）有个老问题：训着训着，被训的模型会摸清评委的系统性毛病并专门利用它——在数学题上表现为写一大堆看起来很严谨的推导，评委给分一路涨，最后答案的正确率却在跌。这篇把评委换成「听两边辩论」：一个模型出解法，另一个专门找这个解法哪一步不对，再由一个能力更弱的评委（Gemini 2.5 Flash Lite 去裁 Flash 级别的策略）判谁有理——弱评委自己解不出题，但能听懂「第三步这里除以了一个可能为零的数」。结果不是峰值准确率高的那两个点，而是曲线不会训着训着崩掉：单人版过了峰就往下掉，而没有真实答案标签的时候你根本不知道该在哪一步停手，冲过头就白训了；辩论版全程把评委的判断力维持住。还有一条可操作的：评委再弱一点会崩得更快，但多加一轮辩论能补回来，也就是监督弱可以拿辩论轮数换。别把它读成「辩论能监督超人类模型」——这里评委和策略的能力差距很小，而且数学题的最终答案可以验证，作者才量得出「它在骗评委」；换到对错本身没法验证的任务上，你连有没有发生这件事都测不出来。

```
Debate maintains peak validation accuracy rather than declining with continued training. This is practically important: without ground-truth labels, one cannot identify the optimal early-stopping point, and overshooting the peak leads to significant performance losses.
```

*作者自己点明：真正的价值在于「不会训崩」，而不是那两个百分点*

### 拿真实事故记录去核对 OWASP 的 LLM 风险榜单

*Incident-Data Robustness Analysis of the OWASP Top 10 for LLM Applications (2026): How a Community-Expert Ranking Holds Up Against a Large-Scale LLM Incident Corpus*

Kyriakos "Rock" Lambros、Steve Wilson · 2026-08-18 · cs.CR · **published August 2026). Not an official OWASP release and does not supersede th**

[arXiv 2608.19266](https://arxiv.org/abs/2608.19266)

![](/assets/img/radar/2608.19266.png)

OWASP 那份「LLM 应用十大风险」排名是一群安全从业者投票排出来的。这篇问：如果按真实发生过的事故来排，顺序还一样吗？作者从公开漏洞库（CVE、GHSA、OSV）和 AI 事故库 AIAAIC 里收了 7714 条 LLM 相关事故，给其中 6639 条按 20 个风险类别打了标签，还专门校正了打标签这一步本身的漏判和误判——用 LLM 给几千条事故分类，它对某几类偏心，那几类在榜上就会虚高，所以先测出每类的准确率再反推真实数量。结果两个榜单几乎对不上：一致性指标 Cohen's κ 约 0.20（这个数扣掉了「瞎猜也能碰上」的部分，0.20 大概是「看着有点像但基本各说各的」），而且误差区间跨过零，等于连「有一点一致」都说不死。有意思的是他们的处理方式：最终榜单还是固定按专家意见占 0.75、数据占 0.25 加权，明知不一致仍让专家主导。另外四个前沿模型分类器谁都没打赢一个笨基线——某类风险在语料里出现次数多就排前面，不做任何加工，平衡准确率 0.863。两点别读歪：一，「不一致」不等于专家排错了，公开漏洞库里能立案的多是有可复现证据的传统软件漏洞，而「在邮件正文里藏一句指令骗过 AI 助手」这种攻击很难被登记成一条 CVE，所以事故语料本身就系统性偏向某几类；二，作者明确写了这是工作组两名成员的探索性分析，不是官方结论。

### 把「别多要权限」训进一个 4B 小模型里

*Task-Conditioned Least-Privilege Learning for Executable Terminal and MCP Agents*

Alexander Tu、Michael Tu · 2026-08-18 · cs.CR

[arXiv 2608.18351](https://arxiv.org/abs/2608.18351)

会用工具的 agent 经常出现这种毛病：你让它「看看日志里有几条 error」，它却把系统日志目录整个提权读了一遍——任务是完成了，但它摸的东西远超需要。这篇不靠运行时拦截，而是把克制训进模型。做法是给每个任务事先划一个「够用就行」的权限圈（比如统计日志错误数：只准读 ./logs 下的文件，只准用 grep 和 wc），agent 实际伸手超出这个圈多少，就记多少超权量，拿这个量当后训练的优化目标。判分不用 LLM 当评委，而是执行完直接查系统状态——该改的文件改了吗、不该碰的目录时间戳变了吗，规则写死，不存在评委被话术骗过去的问题。在 Qwen3.5-4B 上用 1500 个任务训完，2896 次评测里「安全且完成」的比例从 64.36% 提到 98.48%。98% 这个数最容易被误读成「小模型也能安全了」：任务分布是作者自己设计的，「够用权限圈」也是作者自己定义的，留出来测试的任务还是同一套流程生成的。也就是说，训出来的克制是分布内的克制，换一批没见过的工具或环境不能指望它照样收手——作者自己也写明这是对权限系统的补充而不是替代。和 2608.18360 放一起看：18360 说外部闸门串多了会互相拆台，这篇干脆把规则内化到权重里，代价是你再也没法逐条检查它到底遵守了什么。

### 让大模型读 API 手册，自动挖出 PDF 阅读器里的 31 个新漏洞

*From Documentation to Zero-day Vulnerabilities: LLM-Driven Fuzzing of JavaScript Engines in PDF Readers*

Suyue Guo、Stijn Pletinckx、Tianle Yu、Yigitcan Kaya 等 8 人 · 2026-08-18 · cs.CR · **accepted by ACM CCS 2026**

[arXiv 2608.06641](https://arxiv.org/abs/2608.06641)

![](/assets/img/radar/2608.06641.png)

先说清楚：这篇不是「AI 的安全」，被攻破的是 Adobe Acrobat、Foxit 这些 PDF 阅读器内置的 JavaScript 引擎，大模型在这里只是个工具。做法是自动生成海量畸形测试输入去撞程序（俗称模糊测试）。以前这类工具只会试单个函数调用，比如「读取表单里的某个字段」，但真正的崩溃往往要连着来三步——先新建一个字段、再删掉它、然后再去引用这个已经不存在的字段，程序才炸。这篇让大模型去读 API 手册和程序运行记录，从里面提取出「这个参数必须是字符串、第二个参数得是 0 到 4 的整数」这类规则，以及函数之间的先后依赖关系；具体怎么把调用拼成一串合法序列，交给确定性的约束求解器，不让大模型自由发挥。这么分工是为了避开大模型生成测试用例的通病：语法都对，但跑进去就报参数错误退出，什么也测不到。结果是覆盖的代码比现有工具多 48%，找出 31 个此前无人知晓的漏洞，从信息泄露到能直接执行任意代码。数字很硬，但要注意它证明的是「大模型擅长从文档里提规则」，不是「大模型会挖漏洞了」。

### 从图像那一侧去查：概念真的被从扩散模型里删干净了吗

Qianlong Xiang、Miao Zhang、Kun Wang、Haoyu Zhang 等 6 人 · 2026-08-18 · cs.CV

[arXiv 2608.17747](https://arxiv.org/abs/2608.17747)

![](/assets/img/radar/2608.17747.png)

从文生图模型里「擦除概念」（比如让 Stable Diffusion 打死也画不出裸体或某位画家的风格）目前都是用文字来验收的——打这个词进去，画不出来就算擦掉了。这篇换了个问法：文字这条入口被堵上，不代表模型权重里那套视觉规律没了。方法是反着跑扩散过程：拿一张目标概念的图，一步步推回它对应的初始噪声，全程不经过文本通路，看正着跑一遍还能不能还原出来。这篇最值得记的其实是它自己撞上的反例：不加约束地去优化这条噪声路径，连一个完全没训练过的随机初始化模型都能「重建」出目标概念——也就是说重建成功只证明你优化得够狠，不证明模型里真的残留了什么，这类探测很容易自己骗自己。他们加约束就是为了堵这个洞。别读成「现有擦除方法全废了」，它真正立起来的是一条假阳性基线：以后谁声称探出了残留知识，得先证明随机模型探不出来。顺带说清楚归属：这属于版权和有害内容合规那一侧，跟 agent 被网页内容骗着执行指令那条线没有关系。

### 改模型权重来拆掉安全限制，而且一次拆掉一整类话题

*Leveraging Association Context Retrieval in Knowledge Edit- ing to Build White-Box Attacks on LLMs*

Roman Maksimov、Vladimir Aletov、Vladimir Solodkin、Dmitry Bylinkin 等 6 人 · 2026-08-18 · cs.LG

[arXiv 2608.17836](https://arxiv.org/abs/2608.17836)

又一篇需要直接改模型权重的越狱。技术来源是「知识编辑」：先定位出「埃菲尔铁塔在巴黎」这条事实存在哪几层的哪些权重里，再定点改成「在罗马」，尽量不动别的。作者注意到被这样改过的模型，会对改写的目标给出反常高的输出概率，于是把这个特性拿来当攻击：不只针对「怎么造炸弹」这一句改掉拒绝行为，而是先从模型内部捞出一整串相关说法——爆炸物、引信、配比——把整个话题范围的限制一起松开。问题在威胁模型：能改权重的人本来就能直接微调掉安全对齐，绕这么大一圈的增量只是「从一句话扩到一整类话题」。摘要说「不严重损害通用性能」，具体掉多少得看正文。这不是部署环境里的现实风险。今天另有一篇（2608.17829）也在利用模型内部的概率异常，但方向相反——它用异常概率来提前发现模型快要泄露系统提示，一个用来防、一个用来攻，两篇之间没有更深的联系。

### MemCatalyst：用数据投毒放大对视觉语言模型的数据审计

*MemCatalyst: Amplifying Data Auditing on Vision-Language Models via Data Poisoning*

Xukun Luan、Jinyan Liu、Yuhui Gong、Yuanguo Bi 等 7 人 · 2026-08-18 · cs.CR

[arXiv 2608.17722](https://arxiv.org/abs/2608.17722)

艺术家想知道自己的画有没有被偷去训模型，常用的办法是「成员推断」——把一张图喂给模型，看它的输出有多笃定，模型对训练时见过的东西通常更有把握。问题是普通图片这个差距很小，测不出来。这篇的做法是让数据持有者提前动手脚：在自己公开的图和配文之间埋一点故意的错位（图里是一只橘猫，配文却混进一个别处不会出现的怪词），模型训过之后对这种反常组合记得特别牢，审计时一测一个准，而且在不同模型架构之间还能迁移。名字里有 poisoning，但目的是自证权益、不是搞破坏，别归到投毒攻击那栏。跳过的理由是威胁模型的适用范围太窄：必须在数据被爬走之前就埋好、还得埋够量，对已经被训进现有模型的存量数据完全无能为力——而这恰恰是艺术家现在最想问的那部分。另外它证明的只是「埋了记号的数据能被查出来」，推不出「没埋记号的数据有没有被用」。
